# Requirements and acceptance criteria

## Core workflows

### Configure and browse products

**Confirmed (legacy):** `_Sell/Service/DefaultProductRegistry.cs` defines 13 products with integer IDs, names, euro prices, and optional display labels. `_Sell/Action/ProductGrid.cs` and `ProductGridPage.cs` place actions in a 3-column by 4-row grid; the first page also contains `Sonstiges` and `Spende`, leaving three catalog products on the second page. Page navigation wraps at either end. Product buttons show a name, price, and keyboard shortcut (`_Sell/Action/GridHotKeys.cs`). The catalog is compiled into the app, not edited in a settings screen.

**Decision:** products are server-owned PostgreSQL data, maintained in a settings screen. Seed the 13 products in [`CATALOG.toml`](CATALOG.toml) at database initialization; this is the verified current catalog snapshot, and the screenshot is obsolete. Keep the `Sonstiges` and `Spende` special actions.

**Decision (web):** fetch the authoritative catalog from PostgreSQL on page load and cache it for the loaded app session. Product edits are persisted server-side; other loaded sessions do not receive live updates, and a page reload is needed to fetch the latest catalog. Product editing requires connectivity.

### Build and edit a sale

**Confirmed (legacy):** selecting a regular product adds one unit. The item list groups quantities by product `Name`; each click/order operation is also retained separately. The displayed line includes name, unit price, quantity, and extended price; the total is incremented in integer minor units (`_Sell/MainWindow.xaml.cs:101-105, 154-207`). `Price` stores integer cents and formats as euro with comma decimal separator (`_Sell/Model/Price.cs`).

The keypad appends digits to a numeric display; physical number keys and numpad work too. Backspace removes the last digit, the context-menu “Auf Null setzen” resets the entry, and `CE`/Delete removes the most recently added item operation (or clears an already-empty cart) (`MainWindow.xaml:82-159`, `MainWindow.xaml.cs:455-500`). A separate clear-all handler exists but is not directly exposed as a main button.

The `×` keyboard action captures the current integer as a quantity; selecting a product then adds that quantity. The `ENTER` key while waiting for multiplication instead evaluates a number multiplication in the display, so it does not add a product. Other add/subtract/divide handlers implement display arithmetic but are not ordinary sale actions. `GGB` subtracts the current sale total from the amount entered and displays the difference; it is a calculation only, not a payment transaction (`MainWindow.xaml.cs:257-316, 532-600`).

`Sonstiges` prompts for an amount and adds a line named `Sonstiger Artikel`; the amount is interpreted as cents (e.g. `250` means €2.50), because it is passed directly to `Price(int rawValue)` (`MainWindow.xaml.cs:209-223`). `Spende` similarly prompts for an integer-cent amount (`:324-338`).

**Decision:** custom items retain the fixed description `Sonstiger Artikel`; multiple custom entries with different prices remain separate lines. `Spende` remains a distinct informational line in the cart and saved invoice data, but is excluded from invoice total and added to the cash-drawer balance. The legacy code excludes donation from both total and drawer; the rewrite must implement this clarified intention.

**Decision (web):** the cart is an explicit list of lines; each line has quantity controls and a remove action, and the user can undo/remove a line without changing another line's price. Removing a line or discarding the unsaved cart appends compensating cash-ledger entries for the related sale/donation adjustments. The numeric entry workflow for custom items and quantity entry must clearly label units and handle cancellation. Use integer cents end-to-end, with displayed currency formatting separate from entered values. Recalculate invoice totals from chargeable cart lines. Record drawer changes separately in a local audit ledger.

### Complete / save a sale

**Confirmed (legacy):** `SAVE` (also `.` or Print Screen) writes `rechnung_NNNN_yyyy-MM-dd_HHmm.txt` under the per-user AppData `.../.xxyy/_sell/rechnungen/` directory, with date/time, line text, total and a thank-you footer (`MainWindow.xaml.cs:386-424`; `App.xaml.cs:19-24`). The invoice number starts from a small text config and increments after save. The in-progress list is cleared after the save attempt, including when an exception is caught. No receipt printer is invoked.

**Decision:** save informational invoices to PostgreSQL, with no statutory invoice/VAT requirements and no required sequential human numbering. Use a simple invoice record (primary key, timestamp, chargeable total in cents, JSON invoice data). Keep product/line snapshots in JSON so later catalog edits cannot rewrite history. If disconnected after initial app load, queue saves locally and upload when the API is reachable again.

**Decision (web):** saving is deliberate and reports whether the invoice is pending offline or stored on the server. Do not clear the active cart on failed save; a successfully queued offline invoice counts as saved locally. Give queued invoices stable client-generated IDs so retries do not create duplicates. The database stores invoices for later analysis, but the app does not provide an invoice history or reports.

## Business rules and anomalies

- **Money:** legacy prices and totals are integer euro cents. No tax/VAT, discounts, rounding policy, or fractional quantities are implemented. Use integer minor units; do not use binary floating-point for money.
- **Quantity:** regular product button adds one; multiplication mode adds the captured integer quantity when a product is selected. The legacy code does not validate quantity as positive; zero/negative values can arise via arithmetic/display paths. The rewrite rejects zero and negative quantities and accepts positive whole quantities only.
- **Custom item grouping defect:** every custom item is named `Sonstiger Artikel`. The old cart groups by name and overwrites the displayed unit price while summing operation totals. Adding custom items at different prices can therefore show a line extension that does not agree with the sale total. Proposed cart lines should preserve each entered price or group only when unit prices match.
- **Donation discrepancy:** donation uses `AddItemToLists(..., addToTotal: false)` (`MainWindow.xaml.cs:324-330`): it appears as a line priced at the entered amount and contributes zero to total and cash balance. The owner clarified that the intended behavior is to exclude it from invoice total while increasing cash-drawer balance; implement that clarified rule.
- **Undo/cash discrepancy:** undo subtracts the last operation's amount from total and cash, even if cash logging is disabled (`MainWindow.xaml.cs:351-379`). For custom items, the grouped line's price/quantity may become inaccurate. Donation undo uses a zero bookkeeping amount. Replace this with line-based undo and only update a cash balance according to the chosen semantics.
- **Undo crash at default setup:** cash logging is disabled when the stored balance is `-1`; in that state `_cash` is never initialized (`MainWindow.xaml.cs:107-118`). Undo nevertheless dereferences `_cash` unconditionally at `:374`, so undoing a sale can throw. The product-index map also is not adjusted after removing a row, so later cart updates can address the wrong displayed row (`:169-206, 351-379`). These are defects, not intended rules.
- **Cash drawer:** required. Legacy balance is an integer in `cash.int.cfg.txt`; regular sale items added through `AddPriceToList` increase it, and context-menu actions set an absolute amount or subtract a typed amount (`MainWindow.xaml.cs:107-138, 225-255, 579-587`; `App.xaml.cs:65-89, 117-139`). The rewrite starts at €0; balance changes happen as lines are added, and undo/discard adds compensating local-ledger entries. Balance adjustments clamp at €0 and cannot make the balance negative. A local-storage ledger view is available. No payment terminal or tender-record workflow is wanted.
- **Amount received/change:** `GGB` computes entered amount minus total and can show a negative result; it neither validates tender nor records payment. Payments are cash. Keep a simple change helper; denomination/banknote selection is a future idea, not current scope.
- **Receipt defects:** invoice text generation writes the UI's header/separator rows as if they were sale lines (`MainWindow.xaml.cs:401-408`). The file name has minute precision and may collide/overwrite; there is no collision handling. A list-length mismatch returns before closing the file, while the method still reaches clear-all. These are implementation defects, not target requirements.
- **Catalog evidence conflict (resolved):** the current catalog is captured in [`CATALOG.toml`](CATALOG.toml); the screenshot is outdated.

## Acceptance criteria for the web core

1. An authenticated operator can manage products (name, price in cents, optional display name, ordering/active status) through the settings UI; all authenticated users have the same access because there are no in-app roles. Changes persist in PostgreSQL. Database initialization seeds the current 13 products.
2. The operator can select products quickly, enter a positive whole quantity, add fixed-description custom-priced items, and see line extensions and invoice total recomputed exactly in cents. Differently priced custom items remain separate lines.
3. Removing/undoing an item changes only the intended cart line and leaves every displayed line extension equal to its quantity × unit price. Invoice total includes chargeable lines and excludes donation; drawer balance changes include sale items and donations.
4. The operator can distinguish `Speichern` (save) from `Verwerfen` (discard). Discarding an unsaved cart reverses its sale/donation effects through compensating ledger entries. Invalid, empty, overflowing, or cancelled numeric input cannot silently create a malformed line.
5. The operator can calculate change due from an amount received in cash; this does not record a payment. Banknote/coin selection is not required.
6. Online invoice save creates a PostgreSQL record with timestamp, exact total, stable primary key, and JSON snapshots. Offline save queues the same invoice locally with a stable ID, displays pending status, uploads it on reconnect without duplicates, and preserves the queue through a reload after it has been stored locally.
7. Sale additions, donations, and manual drawer adjustments update the browser-local balance and append audit entries including time, reason, and current user's email. An operator can inspect the ledger, set the balance, or subtract a specified amount. The ledger is local and is not tamper-evident or shared between browsers.
8. OIDC settings (issuer, client, redirect, audience/scopes) are supplied at runtime. The frontend uses authorization code with PKCE; the stateless Rust API validates the bearer token and associates actions with the token's `email` claim, whether or not `email_verified` is true. Users are manually provisioned by admins; there are no in-app roles, and only one concurrent user is expected.
9. After initial app/catalog load, checkout and local invoice queueing work offline while the loaded page remains open, even after the access token expires; local events use the identity captured at authentication. Product editing and invoice upload require connectivity, and upload requires a fresh valid token. Pending invoices survive in local storage for upload when the app next runs online. Offline page refresh/recovery and unsaved-cart restoration are out of scope for the first iteration.
10. The app does not depend on live synchronization, inventory, customer records, card processing, external POS hardware, or a receipt printer. Cash denomination selection and invoice history/reports remain out of scope.
